## Premise

Announces prime-rl 0.6.0, which trains trillion-parameter MoE models on heavy agentic workloads. The headline result: **GLM-5.1 trained on SWE tasks at up to 131k sequence length, with sub-5-minute step times and a batch size of 256 rollouts, on only 28 H200 nodes** — step time stays flat as scale grows to 1T parameters. GLM-5.1 is the worked example throughout, but the optimizations are framework-level and apply to any large MoE model (the post names Kimi-K2.7-Code and NVIDIA-Nemotron-3-Ultra-550B-A55B-BF16 as other targets). GLM-5.1 training runs as a single Slurm command: `uv run rl @ examples/glm5_llmd/rl.toml --output-dir /shared/outputs/glm5-llmd`.

## Agentic RL From First Principles

prime-rl embraces asynchronous RL because agentic tasks have long-tail outliers — some rollouts (especially long-horizon coding tasks) run for hours, and waiting for them to finish before updating the policy would idle GPUs. In async RL, trainer and inference are disaggregated and optimized independently; the only hard synchronization point is the policy update itself.

Mechanically: weights are pushed to the inference policy as soon as a new optimizer step completes. Already-dispatched rollouts keep their active prefix cache (not reset), so an in-flight rollout's tokens — and its KV cache — can end up produced by a mixture of policy versions. New rollouts get a fresh KV cache even if they share a prefix with an older one, enforced with a **KV-cache salt**. Requests generated by a policy that's fallen too far behind are dropped, controlled by `max_off_policy_steps` — prime-rl's concrete instantiation of the "policy-lag cutoff" mechanism (see [[frontier-async-rl]]'s policy-lag-K framing, which already attributes a policy-lag cutoff to GLM-5's own training stack).

## Inference Optimizations

**FP8 inference** — used on both prefill and decode, paired with [DeepEP](https://github.com/deepseek-ai/DeepEP) and [DeepGEMM](https://github.com/deepseek-ai/DeepGEMM) kernels, for lower latency and higher throughput. Inference throughput is usually the bottleneck of the whole RL loop.

**Wide Expert Parallelism** — RL inference optimizes for *throughput*, not latency (unlike user-facing serving). The best configuration found is Wide EP: large-scale expert parallelism spanning ≥32 GPUs, combined with a large data-parallel rank (e.g. 32) — a large group of GPUs each holding separate experts and each acting as its own endpoint, synchronized per-layer via dispatch/combine operations.

**Prefill/decode (P/D) disaggregation** — some model↔environment pairs produce as much as a 4:1 prefill:decode token ratio. Serving both from the same workers raises end-to-end latency and erodes the overlap benefit PipelineRL-style async training depends on. Disaggregating means long prefill requests (e.g. lengthy tool outputs) no longer throttle decode workers; decode proceeds at predictable latency, turns complete faster, tool calls reach sandbox execution faster, and the cycle repeats — sometimes across hundreds of turns per rollout.

**KV cache management** — high concurrency (needed for throughput) requires a lot of KV cache space; running short causes cache thrashing and a low prefix-cache hit rate. prime-rl supports tiered offloading to CPU/disk via two backends: **native vLLM offloading** (a single CPU/disk pool per DP-rank worker, only readable by that worker) and **Mooncake Store** (a centralized pool spanning RAM/disk across all nodes, reachable from any inference worker) — Mooncake's centralization is the bigger win once routing gets more sophisticated.

**Request routing** — the default is prime-rl's own fork of vllm-router (minimal, low-config-overhead). An alternative is the **NVIDIA Dynamo router**, which scores workers using live metrics (KV-cache reuse, queue depth, KV-cache utilization, current load) and routes by policy on that score. Paired with Mooncake Store as the centralized KV layer, this gets prefix-cache hits across replicas while balancing load and reacting to live state.

**Router replay (R3)** — trainer↔inference numerical mismatch silently degrades RL training. R3 captures the routing decisions made during inference and replays them on the trainer, which **reduces the trainer/inference KL mismatch by roughly an order of magnitude** and produces more stable training. This isn't free: routed-expert data has shape `[num_layers, top_k, seq_len]`, reaching hundreds of GB per payload and tens of Gbps of throughput at scale. Naively converting that into Python objects (even something as simple as building a dict) causes severe event-loop lag and CPU bottlenecks, so prime-rl treats routed experts as an opaque payload processed entirely with optimized PyTorch ops. R3 composes cleanly with P/D disaggregation.

## Training Optimizations

The trainer is built on [torchtitan](https://github.com/pytorch/torchtitan) (PyTorch-native large-scale training), extended with prime-rl's own FSDP/EP abstractions and improvements.

prime-rl relies on **3-D parallelism** — FSDP, Context Parallelism (CP), and Expert Parallelism (EP) — combined in varying degrees per run; the GLM-5 case study uses all three simultaneously.

- **FSDP** (via PyTorch's `fully_shard` / FSDP2) shards parameters, gradients, and optimizer state across data-parallel ranks, gathered on demand during forward/backward. Required at 1T+ parameter scale to amortize optimizer-state and parameter memory.
- **EP.** Even under FSDP, a single layer can be too large to materialize on one GPU after an all-gather. Concrete math from the post: with 78 layers, 800B parameters, and FP32 master weights, all-gathering one layer needs roughly `(800B × 4) / 78 ≈ 40GB`; with FSDP prefetch overlap of one layer, that's ~80GB just for active-layer weights. EP avoids this by never gathering the full layer — at EP=8, tokens are dispatched and combined via all2all instead, which sharply cuts active memory since experts dominate layer size. prime-rl supports two EP backends: **torch-native all2all**, slightly faster within a single node (e.g. EP=8), and **DeepEP**, which wins by a large margin once EP spans multiple nodes.
- **CP.** At 131k+ sequence length, intermediate *activations* — not parameters — dominate memory, which is what CP shards away by splitting the sequence dimension across ranks. prime-rl supports two general CP schemes: **Ring Attention** (sequence-sharded throughout the forward pass; at attention, each rank holds its Q/K/V shard and exchanges K/V with neighbors in a ring) and **Ulysses** (sequence-sharded through the forward pass, but at attention an all2all flips the layout to head-sharded, computes attention across heads, then flips back) — Ulysses is prime-rl's default and works well with non-standard attention (linear attention, Mamba, etc.). Neither generalizes to GLM-5's **DSA** (DeepSeek Sparse Attention) out of the box, so prime-rl wrote a **custom CP scheme** for it: keep sequences sharded through the projections, then gather K/V across ranks (cheap, since K/V live in a compressed latent space) so the sparse-attention indexer can see the full sequence and compute global top-k indices; core attention then runs only over those fixed-size indices, so cost stays fixed regardless of context length. The whole scheme needs only one all-gather collective per attention layer.
- **GLM-5 DSA kernels** — computed with custom forward/backward kernels adapted from DeepSeek's reference DSA implementation.
- **FP8 training** — via DeepGEMM block-scaled FP8 (the DeepSeek V3 recipe). Contrary to intuition, this does *not* meaningfully raise throughput (quantization overhead eats the gain in most configurations); its real payoff is that it sharply reduces trainer/inference KL mismatch, since both sides now compute in the same precision — and sometimes the exact same kernels — which yields more stable training. This is the same trainer↔inference-mismatch problem R3 attacks from the routing side, attacked instead from the numerics side.
