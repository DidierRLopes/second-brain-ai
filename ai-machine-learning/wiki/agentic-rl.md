# Agentic RL

Most RL post-training for reasoning (see [[rl-training-systems]], [[rl-scaling-laws]]) treats the task as what *The Landscape of Agentic Reinforcement Learning for LLMs* calls **Preference-Based RLHF / PBRFT**: a degenerate single-step MDP where the model emits one response and gets one reward. **Agentic RL** widens this to a full POMDP — multi-turn, tool-using, environment-interacting — where the action space is `A_agent = A_text ∪ A_action` (text generation plus environment actions) and the episode unfolds over many turns before a terminal reward arrives. [Agentic RL: Frameworks and Best Practices (Cameron Wolfe)](../raw/agentic-rl-frameworks-best-practices-wolfe.md) makes the single-turn-vs-multi-turn distinction concrete at the MDP level: single-turn RL's state is just the token context and the transition function deterministically appends tokens, while agentic RL's state is a *joint* state of (text context, external environment state) and the transition function becomes non-deterministic once tool calls are involved (a tool call can return a stochastic observation). This note covers a full cluster of resources that train agents this way: a survey that formalizes the PBRFT/POMDP shift, Wolfe's synthesis of that formulation plus environment-scaling practice, and eight concrete frameworks/papers that each contribute a distinct stabilization, scaling, or environment-synthesis trick. See [[llm-agents]] for the agent architectures being trained and [[swe-agent-benchmarks]] for the executable environments several of these papers train and evaluate in.

## The Landscape of Agentic RL: A Survey

[The Landscape of Agentic Reinforcement Learning for LLMs: A Survey (2509.02547)](https://arxiv.org/abs/2509.02547) — not currently in the repo as a PDF; arXiv link only — is the framing document for this whole cluster. Its central formal move is the PBRFT-to-agentic-RL reframing above: PBRFT's single-step MDP collapses planning, memory, and tool use into a single emitted response, while agentic RL's POMDP formulation makes each of those a first-class part of the action space and the credit-assignment problem.

The survey organizes the field along two taxonomies. A **six-dimension capability taxonomy** — Planning, Tool Use, Memory, Self-Improvement, Reasoning, Perception (plus an "Other" catch-all) — covers what an agentic-RL-trained model needs to do. An **eight-domain application taxonomy** — Search/Research, Code, Math, GUI, Vision, Embodied, Multi-Agent, Other — covers where it's deployed. It names the GRPO/PPO-variant family that recurs across nearly every paper in this cluster: DAPO, GSPO, GMPO, VAPO, Dr.GRPO, ASPO, PAPO, LUFFY, ARPO, KTAE — each a different fix to GRPO's known instabilities (length bias, reward variance collapse, off-policy drift). Its environment compendium (ALFWorld, WebShop, WebArena, SWE-bench, τ-bench, and others) and framework compendium (verl/HybridFlow, OpenRLHF, TRL, AReaL, SkyRL, Verifiers — all covered in [[rl-training-systems]] and [[rl-environments-frameworks]]) make it a useful index even where its own text runs thin: several sections (4.5 Vision, 4.6 Embodied, 4.8 Other, and all of Sections 6–7) could not be retrieved even from the survey's own companion GitHub repository — a gap in the available source material itself, not just a fetch failure, and worth flagging if you go looking for those sections.

## ToRL: Tool-Integrated RL from RL-Zero

[ToRL (2503.23383)](https://arxiv.org/abs/2503.23383) — not currently in the repo as a PDF; arXiv link only — trains tool-integrated-reasoning (TIR) agents (LLMs that interleave natural-language reasoning with executable code) with RL instead of the more common SFT-on-teacher-trajectories approach, which the authors argue "restrict[s] models to predetermined tool usage patterns and limit[s] exploration of optimal strategies." ToRL uses an RL-Zero setup (no post-training warm-start) with a code interpreter added as a tool; code blocks are wrapped in `` ```python ... ``` ``, and a closing ` ```output ` tag pauses generation, executes the code, and appends the result to context. A hard cap of `C=1` tool calls per problem is used in most experiments (`C=2` gives a moderate accuracy gain at a significant efficiency cost), and execution errors are returned to the model truncated to only the last traceback line, to avoid overloading context while still letting the model learn from failure.

The **reward mechanism** is a simple three-way outcome reward (`+1` correct, `−1` incorrect, `−0.5` non-executable code) — except the `−0.5` error penalty turns out not to help: pure outcome reward without the extra code-error penalty matches or exceeds it, on the hypothesis that penalizing errors makes the model overly conservative about generating code at all. Training data is ~29K math competition questions (MATH, Numina-MATH) filtered down using the **LIMR** technique (arXiv 2502.11886), which scores questions by alignment with the model's own per-epoch learning trajectory rather than by raw difficulty. Results: a 14.7% absolute accuracy improvement over an SFT baseline on Qwen2.5-Math-7B, with the fraction of problems solved via generated code rising from ~40% to ~80% over the first 100 training steps — RL is learning *when* to reach for the tool, not just code-generation frequency.

## AgentGym-RL and ScalingInter-RL: Curriculum over Interaction Turns

[AgentGym-RL (2509.08755)](https://arxiv.org/abs/2509.08755) — not currently in the repo as a PDF; arXiv link only — is a generalized, more efficient extension of the prior AgentGym framework for training agents on long-horizon, multi-turn decision-making via pure outcome-reward RL, structured around three components (Environment, Agent, Training) with each environment running as an independent HTTP service. Engineering work to make this scale includes extending the `verl` RL library (originally single-turn) with a `RolloutHandler` that tracks trajectory/reward history and constructs attention/loss masks distinguishing agent- from environment-generated tokens, plus per-environment fixes — e.g. replacing WebArena's single-browser-per-process design with a subprocess architecture so one server manages multiple concurrent Chromium instances, and redesigning SciWorld's init/reset routines for robust parallel instantiation.

Its main algorithmic contribution is **ScalingInter-RL**, a curriculum-learning fix for a specific failure mode: early in training, agents collapse into redundant reasoning loops or pointless actions when given long interaction budgets, but capping training at short horizons forever would prevent the agent from learning genuinely long-horizon behavior. The fix is a monotonically increasing per-phase interaction-turn budget: training splits into `N` phases of `Δ = T/N` steps with budgets `h_1 < h_2 < … < h_N` (concretely `N=3` phases of `Δ=80` iterations with budgets of 8, 12, and 15 turns), hard-terminating the rollout and forcing a final answer once the current phase's budget is hit. A fixed large budget (e.g. 10 turns from the start) gives an initial improvement followed by training collapse; the gradually-increasing schedule is measurably more stable. With this curriculum, models as small as 7B reach performance comparable to much larger closed models on some tasks (26% success on web search, 38.25% on deep research — beating GPT-4o and even Llama-3.1-70B), RL-trained agents show strong test-time scaling along both sequential-turns and parallel-sampling axes, and a 3B model trained with GRPO outperforms a 7B model trained with REINFORCE. RL benefits are uneven across domains — most pronounced on structured, rule-based environments like TextCraft and SciWorld, least pronounced on the noisier, more realistic WebArena.

## DeepSWE: No-Warm-Start Coding Agent and GRPO++

[DeepSWE](https://www.together.ai/blog/deepswe) (Together AI + Agentica / UC Berkeley Sky Computing Lab) is a 32B coding agent (Qwen3-32B base) trained with **no SFT warm-start** — RL from the base model directly — reaching 59% on SWE-Bench-Verified (42.2% Pass@1) for roughly $50K of compute on a 64×H100 Kubernetes cluster. It is built on the **rLLM** training framework and trains against **R2E-Gym** environments (the same procedurally-generated executable gym covered in [[swe-agent-benchmarks]]).

Its main contribution is **GRPO++**, a bundle of fixes layered onto vanilla GRPO: Clip-High (from DAPO), removing the KL loss term entirely, removing reward-standard-deviation normalization, length normalization, a Leave-One-Out baseline, and removing the entropy loss term. The one genuinely novel piece is **Compact Filtering**, DeepSWE's own contribution: it masks the loss for trajectories that hit a timeout, exceed the max context length, or exceed the max step count — these trajectories carry no clean credit-assignment signal (the agent didn't fail at reasoning, it ran out of budget), so training on them as if they were ordinary negative examples introduces noise rather than signal.

The environment-scaling side of this work is its own systems lesson, recounted directly by the R2E-Gym team and synthesized in [Wolfe's agentic-RL overview](../raw/agentic-rl-frameworks-best-practices-wolfe.md): "A challenge we encountered was scaling up SWE-Bench environments… each RL iteration spawned 512 Docker containers in parallel… overloading Docker's API server and eventually crashing the Docker daemon… To remove that bottleneck, we integrated Kubernetes support into `R2E-Gym`, letting the orchestrator schedule containers across a pool of nodes." The general pattern — a naive per-worker local Docker daemon becomes the bottleneck once many rollout workers create/destroy containers concurrently, motivating a cluster-orchestration layer that schedules instances across a node pool and manages lifecycles — recurs across nearly every framework in this cluster that runs thousands of concurrent isolated rollouts per RL update.

## AgentRL: Multi-Task, Multi-Turn Scaling

[AgentRL (2510.04206)](https://arxiv.org/abs/2510.04206) — not currently in the repo as a PDF; arXiv link only — trains a single policy jointly across five distinct multi-turn environments (ALFWorld, a database task, a knowledge-graph task, an OS task, and WebShop) rather than specializing on one domain. Two mechanisms make joint multi-task training work where naive joint GRPO would collapse:

- **Cross-Policy Sampling**: rollouts are drawn from a *pool* of recent checkpoints, not just the current policy — directly analogous to the "proximal policy" trick in AReaL (see [[rl-training-systems]]), but applied for diversity rather than staleness tolerance. The ablation is large: removing it drops average success rate from 65.0% to 60.7%.
- **Task Advantage Normalization**: advantages are z-score normalized *per task*, not globally, so that a task with a different reward scale or difficulty doesn't dominate or starve the gradient signal for the others. Removing it drops average success rate from 65.0% to 59.4%.

With a Qwen2.5-32B backbone and no SFT warm-start, AgentRL reaches 70.4% average success on AgentBench-FC — beating GPT-5 (52.2%), Claude-Sonnet-4-Thinking (58.2%), and DeepSeek-R1 (49.3%) — and generalizes to the held-out BFCL-v3 benchmark (+3.0pp / +1.5pp over baselines), evidence that the multi-task training itself, not just per-domain overfitting, is doing the work.

[Wolfe's overview](../raw/agentic-rl-frameworks-best-practices-wolfe.md) adds the systems mechanics behind both numbers above. The async pipeline runs separate inference and training engines concurrently: the inference engine continuously schedules new rollout jobs as old ones finish, while the training engine pulls *all* completed trajectories (rather than waiting for a fixed batch) for each update, with batch size varying within a configured min/max. Off-policy staleness is bounded by a size-capped data queue that gets fully drained into the trainer every step — "we set a maximum size of the data queue and enforce all trajectories to be moved to the training engine at each step. In doing so, all trajectories are kept as up-to-date as possible with the latest policy." Cross-Policy Sampling is implemented as a model pool drawn from dedicated rollout engines whose weights are updated at staggered frequencies (so different turns *within one trajectory* can come from different policy versions) — empirically this beats the simpler alternative of mixing whole trajectories from different models within a batch. Task Advantage Normalization is a second pass on top of standard GRPO: after computing trajectory-level group-relative advantages and broadcasting them to tokens via the action mask, advantages are re-grouped by task ID and re-normalized to zero-mean/unit-variance per task:

```python
import torch
eps = 1e-8

rewards = torch.tensor([1.0, 0.0, 0.5, 1.0, 0.0, 1.0])      # terminal reward per trajectory
prompt_ids = torch.tensor([0, 0, 1, 1, 2, 2])                 # GRPO groups (same prompt)
task_ids = torch.tensor([0, 0, 0, 0, 1, 1])                   # task/domain per trajectory
action_mask = torch.tensor([[0,1,1,1],[0,1,1,0],[0,1,1,1],
                             [0,1,0,0],[0,1,1,1],[0,1,1,0]], dtype=torch.float32)

# 1) standard GRPO advantage, per prompt group
trajectory_advantages = torch.zeros_like(rewards)
for pid in prompt_ids.unique():
    m = prompt_ids == pid
    g = rewards[m]
    trajectory_advantages[m] = (g - g.mean()) / (g.std(unbiased=False) + eps)

# 2) broadcast to agent-generated tokens
token_advantages = trajectory_advantages[:, None] * action_mask

# 3) re-normalize per task, over only agent-generated token positions
task_normalized_advantages = torch.zeros_like(token_advantages)
for tid in task_ids.unique():
    rows = task_ids == tid
    vals = token_advantages[rows][action_mask[rows].bool()]
    normed = (token_advantages[rows] - vals.mean()) / (vals.std(unbiased=False) + eps)
    task_normalized_advantages[rows] = normed * action_mask[rows]
```

This is the same family of fix as ERPO below (AutoForge), just one granularity coarser — AgentRL normalizes per *task*, ERPO normalizes per *environment*.

## AutoForge: Synthesizing Environments, Not Just Policies

[AutoForge (2512.22857)](https://arxiv.org/abs/2512.22857) — not currently in the repo as a PDF; arXiv link only — addresses a different bottleneck: agentic RL needs environments to train in, and hand-building them doesn't scale. AutoForge automates environment synthesis via tool-graph construction and DAG-structured task generation, then trains on the result with two new mechanisms:

- **ERPO (Environment-level Relative Policy Optimization)**: normalizes advantage at the level of the *environment*, not the rollout group — a finer-grained analogue of AgentRL's task-level normalization, one level down.
- **MEU (Masking Erroneous Users)**: in simulated multi-turn dialogues, a synthetic "user" persona can itself behave incoherently or contradict earlier turns; MEU detects and masks the loss contribution from turns following such errors, so the agent isn't trained to anticipate or paper over a broken user simulator.

AutoForge also introduces **Interleaved Thinking** and **User-Centered Rollout** as harness-level changes, and evaluates on τ-bench, τ²-Bench, VitaBench, and ACEBench-zh — benchmarks specifically built around multi-turn tool-use dialogues with a simulated user, distinct from the single-user executable-environment setting DeepSWE and the SWE-agent benchmarks use.

[Wolfe's overview](../raw/agentic-rl-frameworks-best-practices-wolfe.md) lays out the three-stage synthesis pipeline behind the tool-graph/DAG construction mentioned above: (1) **Environment Generation** — an LLM reads only tool documentation and produces a key-value state space `S=[(K_1,V_1),…,(K_n,V_n)]` plus a Python implementation of each tool, giving `E=(S,F)`; (2) **Task Construction** — the tools are organized into a directed graph (edge = output of one tool feeds another, e.g. `get_project_id_by_name(name) → delete_project(project_id)`), tool-call sequences are sampled via random walks and merged/deduplicated by an LLM, then reasoning nodes are inserted and an LLM predicts edges to form a full solution DAG; (3) **Task Instantiation** — an LLM assigns concrete state values, writes both an explicit task *intent* and a separate, less-explicit user-phrased task *question* (e.g. intent "delete project Auro, create project Lumina" vs. question "Hi, I no longer need the Auro project. Could you please delete it? Also, please create a new project named Lumina."), fills in valid tool arguments, executes the sequence to get a golden final state, and iteratively trims unneeded steps. Reward is binary outcome-only: 1 if the agent's final environment state exactly matches the golden state, 0 otherwise — deliberately outcome-only because multiple valid tool-call orderings can reach the same correct state.

ERPO's three concrete changes: *Interleaved Thinking* retains prior-step thinking traces across turns instead of discarding them before each new generation; *Masking Erroneous User Behavior* uses an LLM judge to detect when the simulated user itself caused a task failure and excludes that trajectory from the loss; and *Environment-Level Advantage Estimation* keeps GRPO's per-question reward mean in the numerator but computes the denominator's standard deviation over *all valid trajectories across all questions sharing the same environment*, pooling variance at the environment level rather than the question level for outlier-robustness. Scale of the synthesis: 10 environments, 1,078 tasks total, generated with Qwen3-235B-A22B-Thinking and used to finetune Qwen3-30B-A3B-Thinking (cold-start SFT on self-collected valid trajectories, then ERPO). Ablations confirm every component matters — interleaved thinking helps despite its added context cost, a stronger simulated-user model at eval time (GPT-5 vs. GPT-4.1) improves measured performance, erroneous-user masking helps, and environment-level advantage estimation is "crucial for keeping agentic RL training stable." Generalization holds even under a deliberately harsh out-of-domain test on AceBench-zh — different prompt/tool-call format, unseen tools, *and* Chinese instead of the English-only training language.

## Agent-R1: A General Synchronous Framework

[Agent-R1 (2511.14460)](https://arxiv.org/abs/2511.14460) — not currently in the repo as a PDF; arXiv link only — is a general-purpose, open framework rather than a single trained model, built around `BaseTool` / `BaseToolEnv` abstractions that let a new tool-using environment be defined without rewriting the RL loop. Its main technical contribution is **Action / Loss / Advantage Masking** for multi-turn credit assignment: in a multi-turn trajectory, only the tokens the policy actually generated (not tool outputs or environment observations echoed back into context) should receive policy-gradient credit, and Agent-R1 masks the loss and advantage computation accordingly at each of three levels. It runs a **synchronous** rollout pipeline — a direct contrast to DeepSWE and AgentRL, which both run async — and uses GRPO as its base algorithm, evaluated on multi-hop QA benchmarks (HotpotQA, 2WikiMultihopQA, Musique) using exact-match.

The central design choice underneath the masking, per [Wolfe's overview](../raw/agentic-rl-frameworks-best-practices-wolfe.md), is representing each trajectory as a sequence of **step-level** records (current/next state, action, feedback, step-level and terminal reward, termination signal) rather than as a flat token sequence or a list of chat-style messages. The message-list alternative introduces **retokenization drift**: "the usual view of a trajectory as one ever-growing token sequence becomes increasingly inadequate: it makes context evolution rigid and creates representation mismatches between rollout and training" — because tokenization isn't perfectly reversible, parsing rollout tokens into chat messages and retokenizing them at training time can desync the trained-on sequence from what was actually generated. Storing full step-level traces (without forcing the agent to see all of them) also enables a configurable **context rule** per environment — append-only, sliding-window, or LLM-summarization — guarding against **context rot** from verbose tool outputs ([[context-engineering]]). Tested on GSM8K, HotpotQA, ALFWorld, and WebShop with Qwen3-4B: GRPO wins on most tasks but PPO wins specifically on WebShop, and on GSM8K the sliding-window context strategy beats both append-only and LLM-summarization — "less is more" on context retention is environment-dependent, not universal.

## RAGEN and StarPO: Self-Evolution via Trajectory-Level Optimization

[RAGEN (2504.20073)](https://arxiv.org/abs/2504.20073) — not currently in the repo as a PDF; arXiv link only — is a modular agentic-RL framework using rule-based, verifiable rewards, framing the training process as **"self-evolution"**: the agent learns from its own generated outputs and the environment rewards those outputs receive. Its algorithmic contribution is **StarPO** (State-Thinking-Actions-Reward Policy Optimization), built specifically to optimize multi-turn interactive trajectories as a single coherent unit rather than treating each action independently: "StarPO treats the entire trajectory — including observations, reasoning traces, actions, and feedback — as a coherent unit for rollout and model optimization."

In a StarPO rollout, the agent's output at each step is a *reasoning-guided structured output* — both a textual reasoning trace and one or more executable actions, not a bare action — and the environment can return an optional intermediate reward (RAGEN specifically penalizes incorrectly formatted output). The rollout ends at a stopping condition or max-turn cap, yielding a final verifiable reward computed over the whole trajectory; the training objective maximizes this cumulative reward but optimizes it over the entire multi-turn trajectory at once, retaining intermediate reasoning traces across steps rather than discarding them between turns — the same instinct as AutoForge's Interleaved Thinking above, arrived at independently for a different environment class.

## Training Long-Context, Multi-Turn SWE Agents with RL

[Training Long-Context, Multi-Turn Software Engineering Agents with Reinforcement Learning (2508.03501)](https://arxiv.org/abs/2508.03501) — not currently in the repo as a PDF; arXiv link only — tackles a systems problem specific to long-horizon coding agents: a multi-turn SWE trajectory can run far past typical context windows. The paper extends context to 131K tokens via YaRN (the same RoPE-extension technique covered in [[positional-encodings]] and reused by Polaris for inference-time scaling, see [[rl-scaling-laws]]) combined with context parallelism, and trains full-parameter (not LoRA) on a Kubernetes-based rollout infrastructure using vLLM.

Two details distinguish it from DeepSWE and AgentRL. First, it runs a **synchronous** pipeline (like Agent-R1, unlike DeepSWE/AgentRL's async setups) and includes an explicit **RFT (Rejection Fine-Tuning) warm-start phase** before RL — the opposite design choice from DeepSWE and AgentRL's "no warm-start" approach, making this paper a useful counterexample to "skip SFT" as a universal agentic-RL recipe. Second, it identifies an **importance-sampling-ratio validity issue** caused by decoding-parameter mismatches between the rollout engine and the training engine — structurally the same train/inference mismatch problem covered in depth in [[frontier-async-rl]], surfacing here in a synchronous rather than asynchronous setting. The paper evaluates on SWE-bench Verified and on SWE-rebench using a temporal train/test split (May vs. June data) to check for benchmark contamination rather than relying on a fixed holdout.

## ECHO: Environment Tokens as a Free World-Model Signal

[ECHO (2605.24517)](../../papers/07-applications/agents-swe/ECHO: Terminal Agents Learn World Models for Free - 2605.24517.pdf) (Microsoft Research: Shrivastava, Awadallah, Papailiopoulos) targets a structural waste in the GRPO-style agentic-RL loop that every paper in this cluster otherwise inherits unmodified: standard training applies the policy-gradient loss only to assistant-action tokens, using a sparse, delayed, outcome-level reward. Every terminal-agent rollout already interleaves actions with environment observations — stdout, errors, file contents, logs, stack traces — and those observation tokens enter the model's forward pass (the model conditions on them when choosing its next action) but never enter the loss. In the paper's own Qwen3-8B setting, often fewer than 15% of on-policy rollouts solve the task, so under plain GRPO the vast majority of rollouts contribute only a uniform negative trajectory-level signal even though they contain rich, specific evidence about how the environment actually responded to each action.

**Mechanism.** ECHO (Environment Cross-entropy Hybrid Objective) adds an auxiliary, length-normalized cross-entropy loss on a subset of environment-observation tokens, trained jointly with the standard GRPO loss on action tokens: `L_ECHO = L_GRPO(θ; A) + λ·L_Env(θ; O′)`, where `A` indexes assistant-action positions and `O′` indexes terminal-output token positions inside the observation blocks (explicitly excluding the harness's own rule-based warning-prefix tokens, which the paper found the model memorizes within ~60 steps and which then stop providing useful gradient). Critically, both loss terms share a single actor forward pass — the same logits already computed for the policy update are gathered at a different set of token positions for the environment-prediction term, so ECHO requires no teacher model, no extra rollouts, and no second forward pass; the only added cost is a masked log-probability sum. The loss-weight sweep (λ ∈ {0.001 … 0.2}) found a productive range of 0.01–0.05, with λ=0.05 used in all reported runs; the auxiliary term is self-annealing because cross-entropy on observation tokens falls rapidly as the policy learns terminal-output statistics, shrinking its own contribution without an explicit schedule. The intuition the authors invoke directly is Sutskever's "predicting the next token well means you understand the underlying reality that led to its creation" — applied here to terminal dynamics rather than text in general: a policy that predicts what a `grep`, a failing test, or a stack trace will say is a policy that has internalized something about what its own commands do.

**Reported results** (TerminalBench-2.0 pass@1, GRPO vs. GRPO+ECHO, identical RL recipe — 16 rollouts/prompt, GRPO, 500 steps, 8×B200): Qwen3-8B improves from **2.70% → 5.17%** (≈1.9×), and Qwen3-14B improves from **5.17% → 10.79%** (≈2.1×), with the Qwen3-14B pass@5 gain (13.48%→19.10%) statistically significant under paired Wilcoxon tests. On internal held-out evaluations (val100, in-distribution; ITD and TBLite, out-of-distribution), ECHO improves every slice for every starting policy tested (Qwen3-8B, Qwen3-14B, and OpenThinker-Agent-v1-SFT). ECHO also reaches GRPO's peak performance in 1.5–2.3× fewer training steps (e.g., Qwen3-8B's aggregate score 1.92× faster, TBLite alone 2.27× faster), and at 14B — where both runs peak at the same step — ECHO instead settles on a strictly higher plateau. Two second-order findings stand out: (1) starting from base Qwen3-8B, GRPO+ECHO matches what an SFT-then-GRPO pipeline buys using ~15K expert demonstrations, without using any of those demonstrations — recovering 101.6% of the OT-SFT gap on val100, 103.9% on ITD, 88.9% on TBLite — and recovers roughly half of the expert-SFT lead on TerminalBench-2.0 (50.0% of the pass@1 gap, 48.6% pass@3, 50.0% pass@5); (2) in a **verifier-free** setting, training with only the environment-prediction loss (no reward signal at all) still improves val100 by +3.8pp and, after filtering to clean tool-call trajectories, lifts the OOD PyTerm and ITD slices by +10pp and +5.2pp respectively — evidence that the environment-observation stream alone, with no outcome reward, is sometimes enough to drive self-improvement on unseen tasks. (This verifier-free trick does *not* transfer everywhere: on TBLite, whose tasks lean on shell orchestration over less-visible filesystem/process state rather than the tightly-coupled code-and-traceback structure of PyTerm, the unsupervised env-loss-only continuation actually degrades performance — the authors attribute this to the predictive signal being weaker when observation structure is less directly coupled to the executed command.)

**Does ECHO actually learn terminal dynamics, or just pass more tests?** The paper runs a dedicated off-policy probe (Section 5.2) to rule out the alternative explanation that ECHO's gains are just better task-solving with no real world-model improvement: it collects rollouts from a *different, stronger* model (Qwen3-32B) on val100/ITD/TBLite, then measures each trained checkpoint's cross-entropy on predicting the resulting terminal-output tokens — a test the evaluated models never saw being generated. Plain GRPO barely moves this number despite improving task success (a sign GRPO doesn't actually improve terminal understanding, just exploits reward). ECHO, by contrast, sharply lowers it across every starting policy and slice: for Qwen3-14B, cross-entropy drops 0.24→0.07 on val100, 0.39→0.31 on ITD, 0.30→0.23 on TBLite; for Qwen3-8B, 0.29→0.07, 0.46→0.32, and 0.35→0.25 respectively. This is the paper's central mechanistic claim — that the auxiliary loss produces a genuinely transferable model of how the terminal responds, not just memorization of the policy's own rollout distribution.

ECHO also changes inference-time behavior, not just pass rate: on TerminalBench-2.0, Qwen3-8B's timeout rate falls from 19.8%→9.0% (−55%) and completion tokens drop 30% (43.2k→30.3k); OT-SFT's timeout rate falls from 45.2%→24.7% (−45%) with 43% fewer agent turns (66.3→37.7). Qwen3-14B is the one exception — timeouts and turns rise slightly (+6%/+7%) — but it still uses 13% fewer tokens while posting the largest TB2 pass@1 gain of the three models, suggesting it reinvests the freed budget into more turns rather than finishing faster. The training corpus itself is also a relevant data point: 8,870 curated terminal tasks (1,977 from Endless Terminals, 723 from OpenThoughts-Agent-v1-RL, plus 6,170 newly generated via a modified Endless Terminals pipeline), filtered to only tasks GPT-5 solved in at least one of 16 attempts — i.e., the training distribution is deliberately calibrated to be solvable-but-nontrivial rather than adversarially hard.

**How this compares to the rest of this cluster.** Every other technique documented above changes *which rollouts count* or *how advantage is normalized* — DeepSWE's Compact Filtering masks out budget-exhausted trajectories as uninformative; AgentRL's Cross-Policy Sampling diversifies *which policy* a rollout is drawn from and its Task Advantage Normalization rescales advantage *per task*; AutoForge's ERPO rescales advantage *per environment*; Agent-R1's Action/Loss/Advantage Masking decides *which tokens* in a multi-turn trajectory receive policy-gradient credit at all. ECHO does not touch any of that — it leaves the GRPO term and its advantage computation untouched and instead adds a second, independent loss term over tokens that were previously masked out of training entirely. It is also the only technique in this cluster that turns *failed* rollouts (which contribute none of the GRPO signal in a near-all-zero-reward regime) into dense training signal, by extracting supervision from the environment-observation tokens those failed rollouts already contain rather than from their (absent) reward. In that sense it is complementary rather than competing: the paper notes ECHO composes orthogonally with policy-gradient-side stabilization tricks like void-trajectory filtering, overlong filtering/clip-higher (the DAPO mechanisms also covered in [[rl-training-systems]]), and KL-regularized reference updates, since it only adds a masked cross-entropy term computed from the same forward pass.

## Cross-Cutting Design Choices

Four axes recur across this cluster and are useful for orienting a new paper into the landscape: **sync vs. async rollouts** (Agent-R1 and the long-context SWE paper run synchronous; DeepSWE and AgentRL run async); **warm-start vs. no warm-start** (DeepSWE, AgentRL, and ToRL skip SFT entirely and start RL from a base model; AutoForge and the long-context SWE paper use a cold-start SFT/RFT phase first); **single-task vs. multi-task** (DeepSWE and ToRL specialize on one domain; AgentRL, AutoForge, and AgentGym-RL all push toward joint or generalized training across many environments, via task-level, environment-level, and curriculum-based mechanisms respectively); and **trajectory representation** (flat token sequences vs. chat-style message lists vs. Agent-R1's explicit step-level records, with the choice driving downstream failure modes like retokenization drift and context rot). A fifth, narrower pattern worth naming on its own: *advantage-normalization granularity* keeps getting reinvented one level at a time — AgentRL normalizes per task, AutoForge's ERPO per environment — which suggests the right granularity is genuinely problem-dependent rather than a solved hyperparameter. None of these axes is settled — the survey's breadth and the disagreement between these concrete training recipes is itself evidence that agentic RL is still in a phase of competing recipes, not a converged one.
